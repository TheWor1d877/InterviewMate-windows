## 异步任务

全部用 asyncio 管理。主要并发任务：

| 任务 | 说明 |
|---|---|
| Audio Capture | 采集音频块 |
| ASR Streaming | 流式识别 |
| Screenshot Capture | 抓取截图 |
| DeepSeek Streaming | 模型流式生成 |
| Dify Retrieval | 知识检索 |
| QuestionManager | 问题处理 |
| TUI Rendering | 界面刷新 |

同步阻塞请求不能放进 UI 主事件循环。音频设备枚举、模型加载这类阻塞操作放进线程执行器。

Windows 默认是 ProactorEventLoop，不支持 `add_signal_handler`，单调时钟分辨率约 15.6 毫秒，超时断言要留余量。

## 请求取消

每个问题会话有一个请求标识，新问题到达时：

- 取消旧问题的生成。
- 旧请求不覆盖当前答案。
- 旧请求后续到达的流式事件不更新新问题的界面。

Esc 取消当前模型任务。Ctrl+N 创建新问题，等价于放弃当前会话并开一个新会话。

取消的实现方式是关闭该请求的响应流并取消对应的 asyncio 任务。用户取消的请求不允许自动恢复。

## 防止重复调用

- ASR 最终结果去重，同一句话不提交两次。
- 相同问题短时间内重复提交去重。
- 相同请求标识不重复启动。
- 用户按 F10 明确重新分析时允许强制重新生成。

去重的键是问题文本的规范化形式加上当前会话标识，规范化去掉空白和标点差异。

前两条分两层实现：同一段录音内重复冲刷出同一句话，在 `app/audio/audio_manager.py` 拦掉；跨录音段重复的同一句话，在 `app/core/question_manager.py` 的会话级去重集合里拦掉。

## 超时管理

分别设置这些超时：

| 环节 | 超时来源 |
|---|---|
| 音频设备初始化 | 配置项 `audio.init_timeout` |
| ASR 初始化 | 配置项 `asr.init_timeout` |
| 截图接口 | 配置项 `screenshot.timeout` |
| Dify 检索 | `rag.timeout` |
| DeepSeek 连接 | `deepseek.connect_timeout` |
| DeepSeek 读取 | `deepseek.read_timeout` |

请求不能放在一个无限等待的任务里。

前三个超时项带默认值（10 秒、60 秒、150 秒），配置文件里不写也能加载，理由见《2-骨架与配置》配置结构一节。

同步阻塞的环节（音频设备枚举、模型加载）放进线程执行器执行，超时到就中断，不许卡住界面主事件循环。超时与其它失败在日志里要能区分开：超时消息里写明超时了多少秒。

模型请求本身由 `app/core/task_manager.py` 托管：请求任务带超时挂在任务表里，同一请求标识不重复启动；超时到直接取消任务本身，不是抛 `TimeoutError` 了事。

## 三种输入的汇合

三种输入进同一个问题处理模块：

```python
class QuestionInput:
    session_id: str
    source: str
    text: str | None
    image_bytes: bytes | None
    timestamp: float
    auto_submit: bool
    confidence: float | None
```

`source` 取 `voice`、`screenshot`、`text`。`auto_submit` 在语音最终结果、截图、手动回车提交时都是 true。

语音和截图合成同一道题，顺序是按一次 F8 → F9 截图 → 再按一次 F8：

```text
面试官说：请实现一个 LRU Cache。
用户按一次 F8 开始语音，识别结果随说话持续产出。
用户按 F9 截图，得到含题目约束与接口说明的图片。
用户再按一次 F8 停止语音，得到这段文字。
合并后一次提交：语音文字加截图图片。
```

合并由事件驱动，没有固定时间窗口：F8 开始后截图先到时暂存图片，等语音最终文本到达再合并；没有语音在采集时截图立即提交。

当前会话只保留最近一张截图和一段语音文本，重新分析时用同一份材料。历史内容不无限累积进每次请求。

截图请求的回复第一行是路由事件 `{"event":"route","kind":"coding"}` 或 `{"event":"route","kind":"normal"}`，模型按图里有没有代码、算法题面或报错栈选 `kind`。右栏收到路由事件先清空上一题残留并按 `kind` 预置形态，后面的 `framework` 不再翻转。`coding` 走 `framework`、`code_delta`、`code_complete` 并要求完整代码；整段 `coding` 没有一条 `code_delta` 时，右栏提示「本次未返回代码，按 F10 重试」，并记 `coding.empty_code`。

会话管理提供这些操作：当前问题会话、创建新问题、添加上下文、清空问题、重新分析。

## 全局快捷键

Windows 下有两个入口：AutoHotkey v2 绑定 F8、F9，在终端失焦时也能用；应用内的按键绑定只在终端有焦点时生效。两者落到同一份动作实现。

AutoHotkey v2 的口径：

- F8 交给 `voice-toggle`，F9 交给 `screenshot`。
- 用 `.venv\Scripts\python.exe -m app.cli hotkey <动作>` 静默调用 CLI，启动时隐藏窗口，不闪黑框，也不改变当前焦点。不要用 `pythonw.exe`：没有控制台时 stderr 是 `None`，日志写到 stderr 会出问题。
- CLI 经 IPC（TCP loopback 加 token）把事件送给主进程，`voice-toggle` 是切换语义。

应用内按键在终端有焦点时直接处理：

- F8 切换采集：按一下开始采集与识别，再按一下停止、冲刷最终文本并自动提交。400 毫秒内的重复触发只真正切换一次。
- F9 按一次截一张图。

外部入口的命令不变：

```bat
interviewmate.cmd hotkey voice-toggle
interviewmate.cmd hotkey screenshot
```

这两条命令通过 IPC 把事件送给主进程，`voice-toggle` 仍是切换语义。

验收：

- 终端切到浏览器后，AutoHotkey 按 F8 开始说话、再按 F8 停止，右栏出现题面并自动作答。
- AutoHotkey 按 F9，终端失焦也能截一张图并提交。
- 终端有焦点时按 F8、F9 由应用直接处理，与 AutoHotkey 不重复触发。

TUI 里的 F8、F9 绑定与 CLI 的 `voice-toggle`、`screenshot` 都落到同一份实现：F8 走 `MainState.toggle_voice_capture`，F9 走 `ScreenshotManager.capture_and_submit()`。生产 `run_main` 给语音开关开 400ms 去抖窗口，窗口内重复的 toggle 直接丢弃并记 `audio.toggle.debounced`，窗口外的调用照常执行。输入框里的 `Ctrl+V` 由应用读 Windows 系统剪贴板后插入；Windows Terminal 原生支持 Ctrl+V，终端自己的粘贴事件照常把内容送进输入框。

## 性能统计

记录这些指标，指标名与取值见《2-骨架与配置》：

| 指标 | 说明 |
|---|---|
| Capture Latency | 截图采集耗时 |
| ASR Latency | 语音识别处理耗时 |
| ASR Final Latency | `AudioManager.stop()` 入口到最终文本产生的耗时，由 AudioManager 记录，flush 解码包含在内 |
| Retrieval Latency | Dify 检索耗时 |
| Request Latency | 请求发起耗时 |
| TTFT | 首 Token 到达耗时 |
| First Framework | 首个框架事件到达耗时 |
| First Item | 首个内容单元到达耗时 |
| Total Latency | 完整输出耗时 |

统计 P50、P90、P95 和最大延迟。

九个指标都接上了：截图采集耗时在 `app/vision/screenshot_manager.py`，`asr_latency` 在 `app/audio/funasr_engine.py`，`asr_final_latency` 在 `app/audio/audio_manager.py`，检索耗时在 `app/retrieval/`，另外四个在 `app/core/question_manager.py`。统计口径见下。

口径：

- `request_latency` 从决定发这次请求算起，到把消息交到模型客户端为止，不含检索耗时，检索单独记 `retrieval_latency`。
- `ttft`、`first_framework`、`first_item`、`total_latency` 一律以「请求交到客户端、开始拉流」那一刻为起点。核心层看不到客户端内部真正发包的时刻，这一段是能观测到的近似，差值在几十毫秒量级。
- 请求被取消时不记 `total_latency`（没有完整输出），已经记下的 `ttft` 等保留。流异常中断时照样记 `total_latency`，它表示到中断为止已经发生的耗时。
- 只认 `item` 与 `code_delta` 算内容单元，兜底事件不计入 `first_item`。
- 检索失败、超时、鉴权失败都要记 `retrieval_latency`，失败也是一次真实等待。

指标值落在进程级记录器里，`interviewmate.cmd status` 能看到统计，结构见《2-骨架与配置》命令行入口一节。

延迟测试用 `scripts/bench_latency.py`，题目集在 `scripts/bench_questions.py`（24 条固定题目，放在仓库里是为了每次跑出来的数字可比较）。runner 走仓库自己的装配函数，请求体由 `PromptManager` 构造，指标取自进程级记录器。

2026-11-26 在本机实测（真 DeepSeek 流式 + 真 Dify 检索，24 条题目全部发出真实请求，Dify 侧 7 次检索全部 200）：

| 指标 | count | P50(ms) | P90(ms) | P95(ms) | max(ms) |
|---|---|---|---|---|---|
| `retrieval_latency` | 7 | 49.6 | 2517.2 | 2517.2 | 2517.2 |
| `request_latency` | 24 | 0.067 | 0.102 | 0.104 | 0.129 |
| `ttft` | 24 | 558.1 | 785.3 | 823.5 | 1080.5 |
| `first_framework` | 24 | 1064.5 | 1501.5 | 1839.8 | 1842.4 |
| `first_item` | 24 | 1302.7 | 2506.4 | 3143.8 | 3272.8 |
| `total_latency` | 24 | 3354.1 | 4488.1 | 4536.9 | 4872.9 |

`capture_latency`、`asr_latency`、`asr_final_latency` 这次没有样本：延迟测试只提交文本，不走截图与语音输入那条路，这三个数字要由真机联调产出。

减少耗时的做法：

- 共用一个 HTTP 客户端，保持连接池，不每次请求重建 TCP 与 TLS 连接。
- 检索只在需要时执行，不检索整个知识库，对检索内容做长度限制。
- 普通算法题不浪费检索延迟。
- 模型输出以简洁为默认目标，限制表达单元数量，先输出框架再输出内容。
- 用户取消后立即停止读取数据。

## 安全与隐私

运行日志写到 `logs/interviewmate.log`，追加写；同一份日志再镜像到按日文件 `logs/interviewmate-{日期}.log`。TUI 启动后日志只落文件，不写 stderr，终端留给界面；`status`、`test`、`devices`、`audio-test` 这类一次性命令仍把日志写到 stderr，命令结果本身走 stdout。

必须满足这些约束：

1. API Key 不写进日志。
2. `.env` 放进 `.gitignore`。
3. 截图默认不长期存储。
4. 录音默认不持久化。
5. 转录文本默认不持久化。
6. 日志只保留请求状态和性能指标。
7. 异常信息里脱敏 API Key 和 Authorization 头。
8. 发送截图前用户明确知道图片内容会提交给云端模型。
9. 密码、令牌这类敏感内容不作为题目发送。
10. 不自动执行模型生成的代码。
11. 不执行危险的 Shell 命令。
12. 外部输入、截图内容和检索内容一律当数据处理，不当可信指令。

配置里的 `privacy` 段控制前三条的开关，默认全关。

## 验收清单

### 输入

- 按 F8 开始采集，再按 F8 停止（切换语义）；终端有焦点时由应用处理，失焦时由 AutoHotkey 触发。
- 语音停止后自动提交，不需要回车。
- ASR 部分结果不触发模型请求，最终结果只触发一次。
- F9 自动完成截图发送，不需要回车。
- 手动输入回车能提交，Shift+回车能换行。
- 截图权限失败不导致程序退出，状态栏出现错误码。
- 设备不可用时提示正确。
- 全局快捷命令能通过 IPC 通知运行中的进程。
- 运行日志写到 `logs/interviewmate.log`，TUI 运行时不写 stderr；`status`、`test`、`devices`、`audio-test` 仍写 stderr。
- 400ms 内重复触发 F8 或 `voice-toggle` 只真正切换一次，并记 `audio.toggle.debounced`。
- 输入框按 Ctrl+V 插入 Windows 系统剪贴板内容；Windows Terminal 原生 Ctrl+V 照常可用。
- 语音与截图按「按一次 F8 → F9 截图 → 再按一次 F8」的顺序合并，没有固定时间窗口。

### 问题处理

- 普通题不调用 Dify。
- 算法题不调用 Dify。
- 项目题调用 Dify。
- 代码题与项目检索能组合。
- 多来源输入能合并。
- 新问题能取消旧任务。
- 重复的 ASR 结果不重复生成。
- 不完整题目能给出合理兜底。
- 截图回复首行的路由事件按 `kind` 预置右栏，非法 `kind` 按 `normal` 处理。
- 路由到 `coding` 但全程没有 `code_delta` 时，右栏提示「本次未返回代码，按 F10 重试」并记 `coding.empty_code`。

### DeepSeek

- API Key 错误能明确提示。
- 连接超时能处理。
- SSE 正常解析。
- 普通文字正常输出。
- 图片正常输入。
- 图片与文字能联合输入。
- 取消请求生效。
- 流式中断不会让界面卡死。
- 模型不按 JSONL 输出时仍有原始内容兜底。

### Dify

- API Key 与 Dataset ID 正常。
- 请求打到检索接口。
- 正确处理返回记录。
- 检索为空能正常降级。
- 连接失败不影响普通问题。
- 返回格式变化不导致程序崩溃。

- 普通题只有两栏。
- 代码题只有两栏。
- 不生成第三个独立面板。
- 左侧标题动态生成。
- 普通题右侧关键点与表达一一对应。
- 代码题右侧上方是思路（步骤与一句话提示），下方是完整代码；普通题右侧是关键点与正文。

- 终端缩小时布局仍可用。

### 性能

必须记录实际测试数据，不接受只声称实时。

- 语音停止到 ASR 最终文本。
- 截图采集到请求发出。

### Windows 平台

- `interviewmate.cmd start` 能启动，缺 `DEEPSEEK_API_KEY` 时以退出码 `3` 结束并指出变量名；`interviewmate.cmd status` 返回六项状态，主进程不在运行时说明进程没在运行。
- `interviewmate.cmd hotkey screenshot` 在主进程运行时返回 `ok: true`，不在时返回 `ok: false` 与 `E_SOCKET`。
- AutoHotkey v2 按 F8、F9 时静默调用 CLI，不弹命令行窗口、不改变当前焦点；终端有焦点时应用内 F8、F9 直接处理，不重复触发。
- `mss` 截图三种目标（`screen`、`primary`、`monitor`）都能抓，失败时状态栏出现 `E_SCREENSHOT` 且程序不退出；截图内容不落盘。
- 音频走 `sounddevice` 麦克风加 `soundcard` 的 WASAPI loopback，麦克风与系统回环都能采到 16000 Hz 单声道。
- 进程回收走 `psutil`：重复启动不产生第二个主进程；`stop` 清理端口文件、token 文件与 PID 文件；端口文件存在但连不上时识别为残留并重建；主进程被强杀后 `status` 判定进程没在运行且不误杀任何进程。
- 安全项：日志文件里搜不到 API Key 值与 Authorization 头的值；截图与录音不落盘。
