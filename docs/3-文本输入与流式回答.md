# 文本输入与流式回答

打通最小可运行闭环：底部输入框敲一句话，DeepSeek 流式返回，终端左右两栏依次显示回答框架和关键表达。

依赖：《2-骨架与配置》。

## 底部输入框

输入框始终显示在底部，不遮挡左右两栏，也不改变两栏比例。

- 回车提交，Shift+回车换行。
- 提交后清空输入框。
- 模型还在生成时可以继续输入并提交下一个问题，提交会取消上一个请求。
- 可以粘贴多行题面。

Textual 的输入框用多行控件 `TextArea`。回车提交，Shift+回车插入换行并阻断默认提交。多数终端发不出 Shift+回车，所以 Ctrl+回车 是等价键，两个键都能换行。粘贴多行题面时保留全部行。

Ctrl+V 由应用自己读系统剪贴板后插入：Windows 侧用 PowerShell 的 `Get-Clipboard -Raw` 读取（显式设 UTF-8 输出编码，中文不乱码），读不到时提示终端原生粘贴键（Ctrl+Shift+V 或右键粘贴）。写入统一用 `Set-Clipboard`。鼠标中键在 Windows 没有 PRIMARY 选区，这里按普通剪贴板读取后插入。终端原生粘贴事件照常进输入框。

## 问题会话

输入结构如下：

```python
class QuestionInput:
    session_id: str
    source: str
    text: str | None
    image_bytes: bytes | None
    timestamp: float
    auto_submit: bool
    confidence: float | None
```

`source` 取值 `voice`、`screenshot`、`text`。`text` 与 `image_bytes` 至少有一个非空。提交时填 `source` 为 `text`、`auto_submit` 为 true、`confidence` 写 null。

`QuestionManager` 负责这些事：

- 接收三种来源的输入，构造 `QuestionInput`。
- 维护当前问题会话，把语音文字与截图图片合并到同一会话。
- 去掉重复提交的内容。
- 判定题型与是否检索。
- 组织模型请求。
- 新问题到达时取消旧请求。
- 保存当前问题上下文，供重新分析使用。

每个问题会话有一个会话标识，每次模型请求有一个请求标识，两者都是 UUID 字符串。新问题到达时旧 `request_id` 失效，旧请求后续到达的流式事件被丢弃，不更新界面。

历史图片与语音不无限累积进每次请求。当前会话只保留最近一次截图与一段语音文本，重新分析时用同一份材料。

## 题型判定

题型枚举取值 `conceptual`、`project`、`coding`、`debugging`、`system_design`、`unknown`。检索需求是独立字段 `rag_required`。

判定先走模型，模型失败或超时再回退本地规则。`QuestionManager` 注入 `DeepSeekQuestionClassifier`，用 `deepseek-flash` 发一次非流式请求，参数固定为 `temperature=0`、`max_tokens=128`、超时 3 秒。输入只有题面，模型只输出一行 JSON：

```json
{"type": "coding|project|system_design|conceptual|unknown", "need_rag": true, "reason": "不超过20字的中文依据"}
```

`type` 只取 `coding`、`project`、`system_design`、`conceptual`、`unknown` 五个值，`need_rag` 是布尔值，`reason` 是简短依据。模型这一路不判 `debugging`，`debugging` 只在回退本地规则时出现。

以下任一情况都回退本地规则，并记一条 `question.classify_fallback` 的 WARNING：回复不是合法 JSON、缺少字段、`type` 或 `need_rag` 取值非法、请求超时、连接失败。回退后提交流程照常继续。`providers.llm=mock` 时不注入模型判定器，不发任何网络请求，直接由本地规则给出结果。

判定结果按规范化后的题面缓存在当前会话里。同一道题按 F10 重新分析直接复用上次结果，不再请求模型；`new_question()` 新建问题时清空缓存。回退得到的结果同样进缓存。

本地规则的判定顺序：

1. 输入含完整代码块、函数签名、报错堆栈，判为 `coding` 或 `debugging`。
2. 输入命中项目类关键词，判为 `project`。
3. 输入含算法题特征，例如要求时间复杂度、给出输入输出样例、提到动态规划或排序，判为 `coding`。
4. 输入含系统设计特征，例如设计一个、怎么架构、保证一致性，判为 `system_design`。
5. 都命中不了，判为 `unknown`。

项目类关键词包括：我的项目、这个项目、我之前的项目、项目中怎么实现、项目架构、我们的服务、我写的代码、我们用的数据库。

本地规则命中项目类关键词时 `rag_required` 置 true；`coding` 与 `debugging` 默认不检索，除非同时命中项目类关键词。模型判定时以模型返回的 `need_rag` 为准。配置里开启强制项目模式时，`rag_required` 恒为 true，模型判定也要服从。

检索是否执行由 `RetrievalPolicy` 单独决定，它只看 `rag_required`，不看题型是谁判的。截图题没有题面文字，题型由模型在回复开头自己判一次，见下面「流式事件协议」里的截图路由事件。

## DeepSeek 客户端

客户端持有一个 `httpx.AsyncClient`，连接池在整个进程生命周期内复用。

对外四个方法：

- `chat_stream(messages)` 发起文本流式请求。
- `multimodal_stream(messages)` 发起多模态流式请求，请求体结构见《接口契约》的「DeepSeek 多模态请求体」。
- `cancel(request_id)` 取消指定请求，关闭对应响应流。
- `check_health()` 探测服务可用性，返回模型能力探测结果，见《接口契约》的「DeepSeek 模型能力探测」。

请求体字段见《接口契约》的「DeepSeek 文本请求体」。`thinking` 与 `reasoning_effort` 按《接口契约》的「DeepSeek 思考模式与推理强度」填。`max_output_tokens`、`temperature` 来自配置。

流式读取要点：

- 用 `client.stream("POST", url, ...)` 拿到响应后逐行读 `aiter_lines()`。
- 每行去掉 `data:` 前缀，剩下 ` [DONE]` 时结束。
- 空的 `data:` 行跳过。
- 每一段增量文本立刻交给事件分发，不在客户端里攒成完整字符串。
- 读到结束前不关闭连接。

异常处理：

- 连接失败、超时、HTTP 4xx 与 5xx 各自映射到《2-骨架与配置》里定义的错误码。
- 任何异常都不能让 Textual 应用退出，错误码显示在状态栏并写日志。
- API Key、Authorization 头、请求体里的图片内容不进日志，脱敏按《2-骨架与配置》里的日志规则。
- 用户取消的请求不再重试。

请求还没收到任何模型输出时，最多按配置的 `max_retries` 重试一次。已经输出部分内容后不重发整个请求。

取消的处理：`cancel` 关闭该请求的响应流，对应的 asyncio 任务收到取消信号后结束。取消是幂等的，对已结束的请求调用不报错。

## 普通问题的 Prompt

Prompt 要求模型先输出回答框架，再按层输出内容。

左侧框架：2 到 3 层，题意简单时两层即可，不硬凑。标题根据题目动态生成，宁少勿多，同类内容合并成一个标题讲透，不把一句话拆成几个标题。

```text
问题：解释 C++ 中 shared_ptr 的引用计数机制。

1. 基本原理
2. 引用计数实现
3. 生命周期与工程约束
```

标题要跟着题目走，不能所有问题都拆成背景、核心内容、项目拓展。左侧不出现技术关键词和具体答案。

右侧内容：整题关键点控制在 5 到 8 个，同主题的机制、同一组对比、同一条链路的相邻步骤合并成一条，用分号在一句里讲完。第一个关键点先说结论，一句话回答这个问题。每个单元是一个关键点加 2~3 句正文，正文承接关键点直接展开，可以写机制、原因、例子和适用边界。关键点与正文在界面上同一行渲染成「关键点：正文」，读起来是段落而不是一串小标题。

输入可能来自语音转写时，Prompt 要求模型先还原用户真正想问的问题，再按还原后的问题回答，不复述语气词与口误。

```text
RAII：通过对象生命周期管理资源，使资源释放与对象销毁自动关联。构造时接管资源，析构时释放，异常路径也不会漏。

智能指针：是对裸指针的封装，通过析构函数管理动态资源。多个智能指针共享对象时，靠引用计数决定何时真正释放。
```

关键点与表达一一对应。句子简短、专业，读完能直接组织成口头回答。单句不超过 30 个汉字，超长拆条；问答题可比代码题略展开。Prompt 里明确禁止模型输出这些栏目：核心概念、关键技术、技术名词解释、通用回答框架、延伸阅读、独立总结、无关提示。

代码题的提示词要求每步 hint 是一句话解法思路，说清方法与原因，并带上与普通题相同的语音转写还原要求，详见《7-代码问题模式》「左侧解题思路」一节。截图提示词由普通提示词继承：在普通题 system 后面追加截图说明与路由规则，这一节的改动会同步带到截图请求。

## 流式事件协议

普通问题的事件定义：

```json
{"type": "framework", "mode": "normal", "sections": [{"id": "s1", "title": "基本原理"}]}
```

```json
{"type": "item", "section_id": "s1", "keyword": "RAII", "sentence": "通过对象生命周期自动管理资源的申请与释放。"}
```

```json
{"type": "section_done", "section_id": "s1"}
```

```json
{"type": "done"}
```

`section_id` 由模型给出，解析时校验它落在 `framework` 声明的 `sections` 里。不存在的 `section_id` 落到兜底区域。

渲染顺序：

```text
收到 framework 事件
        |
立即渲染左侧流程
        |
收到 item 事件
        |
立即渲染右侧对应内容
        |
收到 section_done 事件
        |
左侧该层标记完成
        |
收到 done 事件
        |
整体标记完成
```

截图请求的回复第一行固定是路由事件，格式只有两种：`{"event":"route","kind":"coding"}` 与 `{"event":"route","kind":"normal"}`。图里有代码、算法题面或报错栈时模型取 `coding`，确实没有代码时取 `normal`；截图题默认按 `coding` 处理，拿不准也取 `coding`。解析器把非法或缺失的 `kind` 按 `normal` 处理并记 WARNING。右栏收到路由事件先清空上一题残留，按 `kind` 预置形态，后面的 `framework` 只填内容，不再翻转形态。`coding` 之后走 `framework`、`code_delta`、`code_complete`，必须给出完整代码；`normal` 之后走 `framework`、`item`、`section_done`、`done`。整段 `coding` 一条 `code_delta` 都没有时，右栏提示「本次未返回代码，按 F10 重试」，并记 `coding.empty_code`。

## 解析器容错

模型不保证严格输出 JSONL，解析器要处理这些情况：

- 一条 JSON 被拆到多个网络分片。
- 一条 JSONL 还没收完整就遇到新行。
- 空行。
- 结束事件缺失。
- 模型输出普通文字而不是 JSON。
- 字段缺失。
- `section_id` 在框架里不存在。

做法是维护一个流式缓冲区，只在读到完整换行时尝试解析一条事件。解析成功且字段齐全就更新界面。解析失败的内容进入兜底输出区，原始文本照常显示给用户。

普通文字兜底的做法：识别出不是合法 JSON 的行时，当成普通内容追加到右侧兜底区域，不丢弃。

一条无效 JSON 不能让整个回答崩掉，界面也不能卡在等待状态。流意外中断时，把已收到的内容保持住，状态栏标记出错。

## 终端界面

布局：

```text
+------------------------------------------------------------------+
| InterviewMate | RUNNING | AUDIO | ASR | DIFY | DEEPSEEK | TTFT  |
+----------------------+-------------------------------------------+
|                      | 问题 解释一下 shared_ptr 的引用计数机制   |
|   回答流程           |-------------------------------------------|
|                      | 关键回答内容                             |
|   1. 基本原理        |   RAII：通过对象生命周期自动管理资源。    |
|                      |                                           |
|   2. 实现机制        |   引用计数：复制时增加计数，销毁时减少计数。 |
|                      |                                           |
|   3. 工程约束        |                                           |
|                      |                                           |
+----------------------+-------------------------------------------+
| 输入问题...                                                      |
+------------------------------------------------------------------+
| Enter 提交 · Shift+Enter 换行 · Ctrl+N 新问题 · Esc 取消 Ctrl+Q 退出 |
+------------------------------------------------------------------+
```

状态栏独立于内容区，显示六项，取值见《2-骨架与配置》。状态栏保持紧凑，用短标签不用文字描述。状态栏底色是中性深色，不用高亮色；应用名加粗，标签与分隔符用弱化色，取值用正文色，提示位是错误码时用错误色。

右栏顶部是当前问题，题目加粗，底下一条线把题目与回答内容分开。提交新问题时顶部的题目换成新题目，新建问题（Ctrl+N）时题目清掉。还没有问题时这一段不占位置。

输入框下面一行是快捷键提示，左边列出当前能用的快捷键，右边固定是 Ctrl+Q 退出。左边放不下时从右端去掉整项，右边的退出键始终保留。提示里的键名取自配置里的 `hotkeys` 段，改配置这一行跟着变。F8、F9、F3 对应的功能落地之后再补进这一行。

左右比例 22 比 78。终端宽度小于配置的 `min_width` 时左侧收成紧凑导航，右侧保持足够空间。两栏结构在窄终端下不变。

左侧当前层高亮，已完成层标记完成状态。右侧按模型实际输出顺序流式追加，不生成额外栏目。

右侧关键回答内容放在滚动容器里，内容超出可视高度时用鼠标滚轮上下翻；当前题目固定在滚动区上方不跟着滚。代码区域用 Rich 的语法高亮，同样可滚动。

## 验收

- 底部输入框敲一句话按回车能提交，输入框清空，Shift+回车能换行。
- 提交后右栏顶部显示当前题目，再提交一道题时顶部换成新题目。
- 输入框下面一行显示快捷键提示，右端是 Ctrl+Q 退出，窄终端下放不下的项从右端去掉。
- 状态栏底色不是高亮色，状态行按段着色。
- 提交后左侧先出现标题，再逐条出现关键点与表达。
- 模型的 `framework` 里标题与题目相关，两道不同题目生成的标题不同。
- 框架 2 到 3 层，标题宁少勿多、同类合并；整题关键点 5 到 8 个，第一条先说结论，每条正文 2 到 3 句。
- 回答内容超出可视高度时，鼠标滚轮能把右栏上下翻。
- Ctrl+V 插入系统剪贴板内容，鼠标中键插入普通剪贴板内容；剪贴板读不到时提示终端原生粘贴键。
- 提示词含单句 30 字上限与拆条规则。
- 模型判定返回合法 JSON 时按 `type` 与 `need_rag` 分类；回复非法、超时或连接失败时回退本地规则并记 `question.classify_fallback`。
- `providers.llm=mock` 时不发题型判定请求，只走本地规则。
- 同一道题按 F10 复用判定结果，Ctrl+N 新建问题后缓存清空。
- 截图题第一行的路由事件按 `kind` 预置右栏形态，非法 `kind` 按 `normal` 处理。
- 截图题路由到 `coding` 但全程没有 `code_delta` 时，右栏出现「本次未返回代码，按 F10 重试」。
- 模型输出普通文字而不是 JSON 时，右侧仍然显示原始内容，界面不卡住。
- 模型流中途断开时已显示的内容保留，状态栏出现错误码。
- 生成过程中按回车提交新问题，旧请求的内容不再写入界面。
- 终端宽度缩到 80 列时仍是两栏，右侧不被挤没。
