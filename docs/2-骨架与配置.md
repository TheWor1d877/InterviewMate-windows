## 目录结构约定

包名 `app`，导入路径不带前缀。跨层调用只走事件总线，不直接 import 别的层的实现类。

`app/core/` 放跨模块共享的事件类型与异常。`app/runtime/` 放进程级的东西：PID、socket、状态探测。`app/utils/` 放没有业务含义的小工具。`app/platform/` 放平台相关实现，`get_platform()` 是唯一选择平台的地方，上层模块不判断 `sys.platform`。

## 配置结构

配置文件是 YAML，路径由 `--config` 指定，默认 `config/config.yaml`。顶层键是 `app`、`ui`、`hotkeys`、`audio`、`asr`、`screenshot`、`deepseek`、`rag`、`dify`、`coding`、`privacy`、`providers`。完整内容：

```yaml
app:
  name: InterviewMate
  language: zh-CN
  log_level: INFO

ui:
  left_ratio: 22
  right_ratio: 78
  min_width: 90
  syntax_highlighting: true
  auto_scroll: true
  show_status_bar: true
  show_text_input: true

hotkeys:
  voice_toggle: F8
  screenshot: F9
  new_question: ctrl+n
  cancel: escape
  reanalyze: F10
  show_rag_sources: F3
  quit: q

audio:
  enabled: true
  source: auto
  sample_rate: 16000
  channels: 1
  chunk_duration_ms: 200
  # 音频设备初始化超时（秒），见《8-集成与验收》超时管理一节
  init_timeout: 10

asr:
  enabled: true
  model: paraformer-zh-streaming
  device: auto
  cpu_fallback: true
  vad_enabled: true
  preload: true
  # ASR 模型加载超时（秒），见《8-集成与验收》超时管理一节
  init_timeout: 60

screenshot:
  enabled: true
  target: primary
  monitor: 0
  max_edge: 1600
  format: png
  persist_files: false
  # 截图接口超时（秒），见《8-集成与验收》超时管理一节
  timeout: 150

deepseek:
  base_url: https://api.deepseek.com
  model: deepseek-flash
  stream: true
  thinking: disabled
  reasoning_effort: low
  temperature: 0.3
  max_output_tokens: 2048
  connect_timeout: 5
  read_timeout: 60
  max_retries: 1

rag:
  enabled: true
  top_k: 4
  timeout: 8
  max_context_chars: 8000
  score_threshold_enabled: false
  score_threshold: 0.0
  reranking_enable: false
  force_project_mode: false

dify:
  base_url: http://your-dify-host/v1
  dataset_id: your_dataset_id
  api_key: your_dataset_api_key

coding:
  language: cpp
  standard: cpp17
  submission_mode: auto
  compile_validation: false

privacy:
  persist_audio: false
  persist_transcripts: false
  persist_screenshots: false
  redact_secrets_in_logs: true

providers:
  llm: mock
  retrieval: mock
  asr: mock
  screenshot: mock
```

`providers` 的四个键各取 `mock` 或对应的真实实现名：`llm` 取 `mock` 或 `deepseek`，`retrieval` 取 `mock` 或 `dify`，`asr` 取 `mock` 或 `funasr`，`screenshot` 取 `mock`、`gnome` 或 `mss`。`gnome` 是 Linux 侧的截图实现名（GNOME Shell 扩展静默抓屏，扩展没装时回退 XDG Portal），`mss` 是 Windows 侧的截图实现名。取值不是 `mock` 时必须与当前平台的截图后端名一致，对不上时启动以 `E_CONFIG` 结束。开发期四个键全设 `mock`，真实接入是独立阶段，只换实现不动上层。Windows 侧的实现名见《9-平台差异与Windows适配》。

`screenshot` 取 `mock` 时用内置的假后端：不连 D-Bus、不弹 Portal 窗口，每次采集返回同一张固定的小 PNG，见《4-截图输入与多模态》假截图后端一节。

`retrieval` 取 `mock` 时用内置的假检索后端：不发网络请求，片段取自本地片段池，整条检索链路照常跑；取 `dify` 时走真实知识库检索，接口形状见《6-Dify检索与项目知识》检索接口抽象一节。

`asr` 取 `mock` 时用不加载模型的假引擎：采集照常开关，识别不出文字，第一次按 F8 时不去加载模型；取 `funasr` 时加载本地流式模型，模型与设备参数见《5-语音输入与流式ASR》FunASR 模型一节。

`dify` 段是知识库检索服务的连接参数：`base_url` 是带 `/v1` 前缀的基址，`dataset_id` 是知识库 ID，`api_key` 是知识库密钥。三个字段都能留空，留空时配置照常加载，检索时按没配好处理。`api_key` 只出现在发给 Dify 的 Authorization 头里，配置对象的 `repr` 不带上它，日志里也不出现。

`coding` 段是算法代码题参数，四个字段的默认值是：`language` 取 `cpp`，`standard` 取 `cpp17`，`submission_mode` 取 `auto`，`compile_validation` 取 `false`。配置文件里不写 `coding` 段时用这组默认值。`submission_mode` 的取值与判定口径见《7-代码问题模式》提交格式识别一节。

`deepseek.thinking` 取 `enabled` 或 `disabled`，对应《接口契约》的「DeepSeek 思考模式与推理强度」里的 `thinking.type`。`deepseek.reasoning_effort` 取 `low`、`high`、`max`。`screenshot.target` 取 `screen`、`primary` 或 `monitor`：`screen` 是整屏，多显示器时所有屏拼成一张；`primary` 只抓主屏幕；`monitor` 抓 `screenshot.monitor` 指定的那块屏，序号 0 起数。InterviewMate 不做窗口截图与区域截图，其它目标值在配置校验阶段被拒绝，以 `E_CONFIG` 结束。

`screenshot.monitor` 的序号是 Mutter 内部的显示器枚举序号，0 起数，跟系统设置里的排列顺序不一定一致，插拔显示器后可能变，越界时退回主屏，见《4-截图输入与多模态》截图目标一节。

`rag.force_project_mode` 默认 `false`。开启后所有题目的 `rag_required` 恒为 `true`，不按题型判定，见《3-文本输入与流式回答》题型判定一节。

`audio.init_timeout`、`asr.init_timeout`、`screenshot.timeout` 三个超时项带默认值，配置文件里不写也能加载：分别是 10 秒、60 秒、150 秒。默认值是给新增字段用的，这样用户手写的旧配置不会因为多了一个必填项直接校验失败。三个超时管的是哪一步，见《8-集成与验收》超时管理一节。

`audio.source` 取 `microphone`、`system_monitor`、`mixed` 或 `auto`。前三者按来源挑设备，同类有多台时优先系统默认设备，没有默认标记时取列表第一个；`auto` 在默认麦克风与默认回环都可用时混成一路（来源标签 `mixed`），只有回环时用回环，只有麦克风时用麦克风，两个都不通时报 `E_AUDIO_DEVICE`。默认设备由设备枚举按系统当前的默认输入与默认输出动态解析，配置不绑定具体设备名或索引，语义见《5-语音输入与流式ASR》音频来源一节。解析顺序是三级：先问 `wpctl` 拿 PipeWire 默认 sink 与 source 的 `node.name`，按名字在设备表里精确匹配（默认回环是默认 sink 名加 `.monitor`）；`wpctl` 不可用或匹配不到时退回 `sounddevice` 的默认设备取值（输入按默认输入索引，回环按默认输出名加 `.monitor`）；两级都失败时所有设备按非默认处理。`./interviewmate devices` 在默认设备行末标 `默认`。

配置文件里的值是示例，不是对任意服务版本都成立。模型标识、参数字段、检索方式在写代码时用真实接口验证一次再定稿。

## 环境变量

需要设置的变量：

```ini
DEEPSEEK_API_KEY=your_deepseek_api_key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash

DIFY_BASE_URL=http://your-dify-host/v1
DIFY_DATASET_ID=your_dataset_id
DIFY_DATASET_API_KEY=your_dataset_api_key
```

`.env` 不进 Git，权限设成 `600`。环境变量覆盖配置文件里的同名项。

`DIFY_BASE_URL`、`DIFY_DATASET_ID`、`DIFY_DATASET_API_KEY` 分别接到 `dify` 段的 `base_url`、`dataset_id`、`api_key`，变量有值时覆盖配置文件里的同名项，没设时用配置文件里的值。

`DEEPSEEK_API_KEY` 只在 `providers.llm` 指向真实实现（`deepseek`）时必填。`providers.llm=mock` 时不查这个变量，缺它也照常启动。

## 日志

级别分 `DEBUG`、`INFO`、`WARNING`、`ERROR`，默认 `INFO`。

每条日志带 `ts`、`level`、`event`、`request_id`、`session_id`。没有会话上下文的启动期日志，后两个字段写 `-`。

脱敏在日志封装层做，规则是：匹配 `Authorization` 头的令牌、匹配 `sk-` 开头的字符串、长度超过 1024 字符的 base64 片段，一律换成 `***`。`Authorization` 头保留 `Bearer` / `Basic` 方案名，只替换令牌部分。脱敏在写入前完成，不影响调用方传入的内容。

`request_id`、`session_id` 这两个专用槽位在塞进日志记录的 `extra` 之前先过一遍脱敏，内存里的日志记录不留原文。

日志行以空格分隔，开头是时间戳与级别，其余字段是 `key=value`。字段值里的空白字符渲染时换成 `-`，防止值里的空白伪造出额外的字段。替换字符不能用 `_`，`_` 会让 `sk-` 开头的密钥绕开脱敏。

日志写到 `logs/interviewmate-{日期}.log`，默认同时输出到终端；TUI 运行时另写稳定文件 `logs/interviewmate.log`（追加），日志只落文件、不写 stderr，`status`、`test`、`devices`、`audio-test` 这类一次性命令仍写 stderr。TUI 启动时还摘掉根记录器上写终端的 handler 并补一个 `NullHandler`，第三方库后来调 `logging.basicConfig()` 挂不回来（funasr 导入时就把 httpx 的 INFO 请求日志按自己的格式打到 stderr）；界面运行期间第三方库用 `print()` 打的提示（如 torchaudio 的 ffmpeg 通知）追加进 `logs/interviewmate.log`。

## 命令行入口

支持的命令：

```bash
./interviewmate start
./interviewmate warmup
./interviewmate stop
./interviewmate status
./interviewmate test
./interviewmate devices
./interviewmate audio-test
./interviewmate hotkey voice-toggle
./interviewmate hotkey screenshot
```

Windows 侧用 `interviewmate.cmd` 或 `python -m app.cli`，见《9-平台差异与Windows适配》。

退出码：

| 退出码 | 含义 |
|---|---|
| 0 | 正常 |
| 1 | 运行错误 |
| 2 | 参数错误 |
| 3 | 配置缺失或校验失败 |

`start` 按顺序做这些事：

1. 读配置，校验必填项；`providers.llm` 指向真实实现（`deepseek`）时缺 `DEEPSEEK_API_KEY` 以退出码 `3` 结束并说明缺哪个变量，`providers.llm=mock` 时不查这个变量。
2. 检查依赖包是否可导入，缺包时报出包名。
3. 检查音频设备，失败只告警不退出。
4. 检查截图接口是否可用，失败只告警不退出。
5. 建 asyncio 事件循环。
6. 建 Unix Domain Socket 并开始监听。
7. 初始化 DeepSeek 客户端，探测模型能力，见《接口契约》的「DeepSeek 模型能力探测」。
8. 检查 Dify 可用状态，失败时把状态标成 `degraded`。
9. 按配置预加载 ASR，失败时标成 `error` 并继续。
10. 启动 Textual UI。

`test` 做一次只读自检，不启动 UI，不驻留模型：检查配置能否加载并通过校验、依赖包能否导入、音频设备能否枚举、截图接口能否探测、ASR 能否加载，再按 `providers` 决定要不要探测 DeepSeek 与 Dify。逐项打印结果，失败项带上本节错误码表里的错误码。全部通过退出码 0，有失败项退出码 1。`providers` 指向 `mock` 的能力不连真实服务，对应项打印 `mock`。

`warmup` 在主进程运行时通过 socket 通知主进程预热 ASR、建立 HTTP 连接、探测模型、探测 Dify、刷新设备列表。预热结束后模型留在主进程里。主进程没运行时，`warmup` 只做环境检查与可用性检查，输出里不能声称模型已驻留内存。

`stop` 通过 socket 通知主进程，依次停止音频采集、取消模型任务、结束 ASR 流、关闭 HTTP 客户端、移除 socket 文件、清理 PID 文件、退出 UI。

`status` 通过 socket 问主进程要状态。主进程没运行时直接读 PID 文件判断，输出里标明进程不在运行。

```text
InterviewMate: RUNNING
PID: 12345

Audio: STOPPED
ASR: READY
DeepSeek: READY
Dify: READY

Current Task: IDLE
```

状态字段的具体取值：

| 状态项 | 取值 |
|---|---|
| RUNNING | `running`、`stopped` |
| AUDIO | `off`、`on` |
| ASR | `idle`、`loading`、`ready`、`error` |
| DIFY | `offline`、`ready`、`degraded` |
| DEEPSEEK | `idle`、`connecting`、`streaming`、`error` |
| TTFT | 毫秒数，没有数据时显示 `-` |

AUDIO、ASR、DIFY 这三项的含义：

| 状态项 | 取值 | 含义 |
|---|---|---|
| AUDIO | `off` | 没在采集音频 |
| AUDIO | `on` | 正在采集音频 |
| ASR | `idle` | 模型还没加载过 |
| ASR | `loading` | 正在加载模型 |
| ASR | `ready` | 模型就绪，可以识别 |
| ASR | `error` | 模型加载失败 |
| DIFY | `offline` | 没连真实的 Dify 服务 |
| DIFY | `ready` | 检索正常完成 |
| DIFY | `degraded` | 连上了但检索出问题，回答按降级继续 |

`providers.retrieval` 取 `mock` 时用假检索后端，不连外部服务，DIFY 是 `offline`。`providers.asr` 取 `mock` 时用不加载模型的假引擎，ASR 状态照样走到 `ready`，但识别不出文字。

状态 payload 里还带一个 `metrics` 段，是各指标的统计列表，元素形如 `{"name": "capture_latency", "count": 3, "p50_ms": 12.3, "p90_ms": 14.0, "p95_ms": 15.0, "max_ms": 15.0}`。只包含已有样本的指标，按性能指标一节的指标顺序排；没有样本时是空列表。`./interviewmate status` 把这一段打印在六项状态之后。

## 进程通信

本节是 Linux 侧实现。协议层两平台共用，Windows 侧的传输层见《9-平台差异与Windows适配》。

传输层走 `app/platform/` 门面。Linux 侧是 AF_UNIX socket 文件，Windows 侧是 TCP loopback 加端口文件加随机 token，两边的请求与响应格式一样，`app/runtime/socket_protocol.py` 只有一份。

socket 文件默认在 `runtime/interviewmate.sock`，路径由 `app/runtime/process_manager.py` 里的常量 `SOCKET_PATH` 决定。

请求是单行 JSON，字段 `action` 取值 `voice-toggle`、`screenshot`、`stop`、`status`、`warmup`，可选字段 `request_id`。响应是单行 JSON，字段 `ok` 是布尔值，`error` 是字符串，`payload` 是对象。

客户端连上后发一行请求、读一行响应、断开连接。

`action` 的处理：

| action | 行为 |
|---|---|
| `voice-toggle` | 切换语音采集状态 |
| `screenshot` | 触发一次截图 |
| `stop` | 走 `stop` 的收尾流程 |
| `status` | 返回当前状态 |
| `warmup` | 触发预热 |

界面 F8 与 socket 的 `voice-toggle` 都调到 `MainState.toggle_voice_capture`。生产 `run_main` 启用 400ms 去抖（常量 `VOICE_TOGGLE_DEBOUNCE_SECONDS`），窗口内重复调用直接丢弃并记 `audio.toggle.debounced`。

`voice-toggle` 返回的 payload 有五个字段：

| 字段 | 含义 |
|---|---|
| `audio` | 采集状态，取 `on` 或 `off` |
| `asr` | ASR 状态，取 `idle`、`loading`、`ready` 或 `error` |
| `result` | 这次动作的结果标识，取 `started`、`stopped`、`empty`、`error` 或 `ignored` |
| `text` | 最近一次语音识别出来的最终文本，没有时是空串 |
| `note` | 结果标识翻成的一句人话 |

主进程建 socket 服务端时如果端点文件已存在，先连一次确认有没有活进程占用，有活进程就以退出码 `1` 结束，没有就删掉旧文件重建。正常走 `start` 时旧实例已在回收阶段停掉，这一步只作兜底。

PID 文件写主进程 PID，`start` 时检查文件里的 PID 是否对应活进程。

`start` 前先回收上一次留下的主进程，流程见 `app/main.py` 的 `stop_stale_instance`：

1. 通信端点上有活进程：先发 `stop` 并等它自己退出，最多 10 秒。
2. 没退出的按 PID 文件与 `/proc` 扫出的本仓库进程发 `SIGTERM`，再等 5 秒，仍在就 `SIGKILL`。
3. 回收后端点仍被占用或者还有本仓库进程活着：放弃启动，退出码 1。
4. 清掉残留的 PID 文件与端点文件，然后照常启动。

回收只认本仓库的启动命令：`python -m app.cli start` 或 `python -m app.main`，并且工作目录或 `PYTHONPATH` 指向本仓库。PID 文件里的 PID 被系统复用、指向别的进程时只当残留文件删掉，不结束它。配置、依赖与终端检查都在回收之前，检查没过不动正在跑的进程。回收过程写 `start` 的输出与日志，日志事件名是 `main.reclaim`。

## 错误码

状态栏和日志用同一套错误码：

| 错误码 | 含义 |
|---|---|
| `E_CONFIG` | 配置缺失或校验失败 |
| `E_AUDIO_DEVICE` | 音频设备不可用 |
| `E_ASR_LOAD` | ASR 模型加载失败 |
| `E_ASR_DECODE` | ASR 解码失败 |
| `E_SCREENSHOT` | 截图接口不可用或被拒绝 |
| `E_DEEPSEEK_AUTH` | DeepSeek API Key 无效 |
| `E_DEEPSEEK_TIMEOUT` | DeepSeek 请求超时 |
| `E_DEEPSEEK_STREAM` | DeepSeek 流式读取中断 |
| `E_DIFY_AUTH` | Dify API Key 无效 |
| `E_DIFY_TIMEOUT` | Dify 检索超时 |
| `E_DIFY_RESPONSE` | Dify 响应格式异常 |
| `E_DIFY_REQUEST` | Dify 拒绝检索请求体 |
| `E_DIFY_QUERY_TOO_LONG` | 检索查询超过长度限制 |
| `E_SOCKET` | IPC 通信失败 |

`E_SOCKET` 两平台共用。Windows 侧把这一项细分成端口文件不存在、端口文件存在但连不上、token 不匹配三种情况，见《9-平台差异与Windows适配》。

## 性能指标

每个指标记毫秒值和来源：

| 指标名 | 含义 |
|---|---|
| `capture_latency` | 截图采集耗时 |
| `asr_latency` | 语音识别处理耗时 |
| `asr_final_latency` | `AudioManager.stop()` 入口到最终文本产生的耗时，由 AudioManager 记录，flush 解码包含在内 |
| `retrieval_latency` | Dify 检索耗时 |
| `request_latency` | 请求发起耗时 |
| `ttft` | 首 Token 到达耗时 |
| `first_framework` | 首个框架事件到达耗时 |
| `first_item` | 首个内容单元到达耗时 |
| `total_latency` | 完整输出耗时 |

指标值落在进程级记录器里（`app/utils/timing.py` 的 `default_recorder()`），`./interviewmate status` 能看到统计，统计口径见《8-集成与验收》性能统计一节。

## 验收

- `./interviewmate start` 能启动；`providers.llm=deepseek` 时缺少 `DEEPSEEK_API_KEY` 以退出码 `3` 结束并指出变量名，`providers.llm=mock` 时缺这个变量也照常启动。
- `./interviewmate status` 在主进程运行时返回上面那份状态结构，主进程不在运行时明确说明进程没在运行。
- `./interviewmate hotkey screenshot` 在主进程运行时返回 `ok: true`，主进程不在运行时返回 `ok: false` 与错误码 `E_SOCKET`。
- 日志文件里搜不到 `DEEPSEEK_API_KEY` 的值和 `Authorization` 头的值。
- 配置文件里出现《接口契约》里退役的模型名时，`start` 报配置错误并列出被拒绝的名字。

Windows 侧验收见《9-平台差异与Windows适配》。
